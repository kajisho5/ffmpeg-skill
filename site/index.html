How it works

It stops guessing.

An agent that “knows FFmpeg” still guesses: it assumes a frame rate, picks a codec the container cannot hold, re-encodes a file that only needed a stream copy, and reports “done” without opening the result.

  1. Real files first

    Every job starts with probe.py. The agent decides from the measured duration, fps, resolution, colour and audio layout, not from the file name.

  2. Structured tools, not shell strings

    Each operation is a script with typed arguments. Nothing runs through a shell, and no filter graph is accepted from the caller.

  3. A contract the agent can read

    contract --json states, for every tool, what it takes, what it writes, which FFmpeg components it needs and how the result is verified.

  4. Verification after execution

    The result is probed, checked against the destination’s spec and, when the picture changed, looked at as a contact sheet.

  5. Local first

    No cloud, no API keys, no Python dependencies. Optional speech-to-text runs on an engine you install, and the audio is never uploaded.

Built for agents

  • MCP

    Every tool is an MCP tool. A core 12 is listed by default to keep the client’s context small, all 42 with FFMPEG_SKILL_MCP_FULL=1.

    tools/list · tools/call

  • Contract

    One machine-readable contract describes the whole set: what each tool takes and writes, what it needs from FFmpeg, and how it is checked.

    contract --json

  • SPEC

    Each tool’s input schema is derived from the script’s own argument parser, never written by hand beside it. CI fails if the docs drift.

FAQ

Questions people ask first

Can I pass raw ffmpeg arguments, or a filter_complex?
No. Each operation is a script whose flags are its own argument parser, and that parser is what the contract and the MCP schema are built from. A caller-supplied filter graph, -vf string or other ffmpeg option is not an argument any script accepts.
Why 42 tools? Isn’t that overkill?
One tool per job, because each job promises something different and the tool measures that promise after the run. An agent does not read 42 schemas: over MCP it sees a core 12 and calls the other 30 by name when a job needs one.
What does “verified” check, and what can it not tell me?
It covers what can be measured from the file: that it opens, its length, codecs, size and frame rate, and the tool’s own promise, such as loudness after normalising. A value that cannot be read fails as not_measured instead of passing. Whether it looks or sounds right is listed as unverified, so you look at the contact sheet.
How does ffmpeg-skill compare with Remotion?
They complement each other. ffmpeg-skill edits footage you already have; Remotion renders a video from React components. remotion-ffmpeg-skill joins the two: it measures with this repo, draws in Remotion, then checks and delivers with this repo again.
Does it encode on the GPU?
On Apple Silicon, with VideoToolbox, when you ask for it with --hw or FFMPEG_SKILL_HW=1. Other GPU encoders are reported by doctor when your FFmpeg has them, but no tool encodes with them.
